# 开发流程

本页是辅助中文译文，以[英文原文](../en/process.md)为准。

<a id="overview-and-evidence-index"></a>

## 总览与证据索引

一个梳理完成的公开任务依次经过 PM、Engineer 和独立 QA，然后验证发布结果。

[E1 角色](team.md)、[E2 测试边界](testing.md)和 [E3 真实活动](tracker.md#current-role-activity)定义交接方式。

<a id="workflow"></a>

## 工作流

1. PM 阅读目标，创建或更新公开任务，定义可观察验收标准、允许文件、基线和排除范围。
2. Engineer 阅读任务与仓库上下文，报告冲突，仅实施批准范围。
3. 产品改动先通过接口、集成或系统测试复现预期行为，再实施并运行适当检查。
4. Engineer 通过任务内 JSON 交付向 PM 报告改动文件、实际检查、限制和未完成标准。
5. 独立 QA 代理审核最终差异，逐项验证标准，包括回归、隐私和发布范围。
6. 不通过的标准退回 Engineer 修复；QA 复验后，PM 在用户授权下发布通过审核的改动。
7. PM 验证已推送分支及公开链接，在任务中记录证据，任务关闭遵循约定的负责人流程。

纯文档任务检查链接、锚点、命令和发布结果，不假装执行了产品测试套件。

<a id="evidence-rules"></a>

## 证据规则

每个任务保留一个目录，`evidence/` 放原始输出，`scripts/` 放临时工具，`tmp/` 放 JSON 交付。

权威英文文档放在根目录 `README.md`、`AGENTS.md` 及八份 `docs/en/` 模块中；仅在 `docs/ch/` 维护一套完整的辅助中文译文。

英文原始 Markdown，包括链接目标和代码块，不得包含中文字符或 CJK 标点；使用 ASCII 路径、双向语言链接，两套文档的事实、命令和状态须一致。

仅可发布精确允许列表中的项目文档；任务私有证据保持忽略，不保留任务目录中的公开副本。

事情发生后才记录，区分历史报告与当前检查，不得编造代理之前使用任务跟踪的经历。

后续路线图批次必须先单独梳理并确定验收标准，再开始实施。
